# 导入管线重新设计

> **状态（2026-11-27）**：七步都已实现，分在四个从 `main` 开的分支上（§10），复测见 §1.6 到 §1.8，都还没合并。依据是同日的实测（§1）和评估 [review/2026-11-26-导入管线评估.md](review/2026-11-26-导入管线评估.md)。测量脚本在 [scripts/bench-import/](../scripts/bench-import/README.md)，每一阶段做完都用它复测。

## 1. 测出来的

**测试集**：用内置样片生成 500 张，400 张 2400 万像素 JPEG（6000px）加 100 张 1200 万像素 HEIC，共 3.6 GB，每张内容和拍摄时间都不同。
**机器**：M3 Pro 12 核、18 GB，本地 SSD，文件已在系统缓存里（热缓存），开发用的 Python 3.14。导入用默认设置：不做 HD、做颜色、相似照片带特征向量。

### 1.1 一次全新导入：21 秒

| | 耗时 | 占比 |
|---|---|---|
| 整个导入（两次：20.7 / 21.2 秒） | 21 s | 100% |
| 出缩略图（索引期间分批出） | 19.7 s | 95% |
| 索引 500 个文件（ExifTool 0.27 s、指纹 0.30 s、写库约 0.1 s） | 0.8 s | 4% |
| 507 次提交 | 0.08 s | |
| 第一遍数文件 | 0.006 s | |
| 索引后的缩略图补漏 | 0.02 s | |

出图线程那边：6 个线程合计 107 秒，基本全是 Pillow 解码和缩放；平均 5.4 个核在忙。写库的主线程有 11.9 秒在等出图，7.3 秒在取颜色（每张 14.6 ms）。

### 1.2 单张成本（不并发）

| | JPEG 24 MP | HEIC 12 MP |
|---|---|---|
| 现在：Pillow 出 512 缩略图 | 62 ms | **601 ms** |
| 系统 ImageIO，进程内 | 41 ms | 70 ms |
| 系统 ImageIO，6 个进程并发时 | 56 ms | 125 ms |
| 从缩略图取颜色 | 11 ms | 11 ms |

HEIC 只占 20% 的文件，却占了约 70% 的出图时间。用 ImageIO 6 路并发出完这 500 张缩略图要 **6.4 秒**（现在 19.7 秒）。

出图线程从 6 个加到 12 个，导入只从 21 秒降到 19 秒，线程合计时间却从 107 秒涨到 166 秒：瓶颈在解码器和 GIL，不在线程数。

### 1.3 导入以后

| | 耗时 |
|---|---|
| 人脸识别 500 张（一个 worker，约 1 个核，每张 228 ms） | **114 s**，是导入的 5.5 倍 |
| 两个 worker 同时跑（各跑一个图库） | 各 125 s，合计吞吐 1.82 倍 |
| 重新导入同一个文件夹（500 张都没变） | 1.1 s，每张 2.2 ms |

测试集是风景照，没检出人脸，但每张照片的检测成本照样要付。

### 1.4 没测的

AI 标注（要花钱调接口，按每次请求 2 到 5 秒、3 个并发估算，500 张要 6 到 14 分钟）、冷缓存、外接盘和 NAS、RAW、视频、Windows、打包后的版本（PyInstaller，Python 3.12）。

### 1.5 结论

1. **导入的时间就是出缩略图的时间。** 索引、写库、遍历目录、提交加起来不到 5%。评估里猜的「索引和出图不重叠」「目录走两遍」「每个文件提交一次」，在本地盘上都可以忽略。
2. **HEIC 走 Pillow 是最大的一块。** 换成系统 ImageIO，HEIC 快 8.6 倍，JPEG 快 1.5 倍。
3. **缩略图变快以后，主线程取颜色会成为新瓶颈**：500 张要 7.3 秒，比 ImageIO 出完全部缩略图的 6.4 秒还长。
4. **导入完以后最慢的是人脸识别**，而且只用一个核。多开 worker 基本线性提速。

### 1.6 第 1 步之后（颜色挪到出图线程）

同一台机器、重新生成的同一种测试集，改动前后交替各跑两次，每次新图库。原始输出在 `scripts/bench-import/results-2026-11-26/step1-*.json`。

| | 改动前 | 改动后 |
|---|---|---|
| 整个导入 | 18.3 / 17.6 s | 18.7 / 18.4 s |
| 主线程取颜色 | 6.3 / 6.0 s | 0（挪走了） |
| 主线程写颜色 | 含在上一行 | 0.14 / 0.13 s |
| 出图线程取颜色（各线程相加） | 0 | 6.7 / 6.6 s |
| 主线程空等出图 | 10.5 / 10.4 s | 17.0 / 16.9 s |

- 两边写进库里的颜色（3784 行）、相似照片哈希、缩略图、横竖方向逐行完全一致。
- 主线程的活从 6 秒多降到 0.1 秒，但整个导入慢了约 0.6 秒（3%）。原因：出图还是瓶颈，改动前主线程取颜色等于多了第 7 个干活的线程；现在这 6.6 秒摊进了 6 个出图线程，每个多出约 1.1 秒。
- 所以第 1 步单独合并是轻微的退步，收益要等第 2 步：出图交给 ImageIO helper 以后，出图线程大部分时间在等 helper 回复，取颜色正好填进去；留在主线程的话，它要串行 7 秒，比出完全部缩略图的 6.4 秒还长。
- 这一批的两边都比 §1.1 的 21 秒快约 3 秒，测试集是重新生成的，原因没有细查。前后比较只看本节同一批的数字。

### 1.7 第 2 步之后（Mac 上 JPEG、HEIF 走 ImageIO）

测试集换了一批：HEIC 用系统的 `sips` 编码（`make_dataset.py --sips`，和 iPhone 存的一样，生成只要 4 分钟，不用 12 分钟），其余同 §1.1。`main`（改动前）和这个分支（第 1、2 步）交替各跑两次，原始输出在 `scripts/bench-import/results-2026-11-26/step2-*.json`。

| | `main` | 第 1、2 步 |
|---|---|---|
| 整个导入 | 13.9 / 14.1 s | **7.4 / 7.4 s** |
| CPU 合计（含 ExifTool 和 helper 进程） | 98 / 101 s | **31 s** |
| 出图线程（各线程相加） | 68 s（Pillow） | 27 s（等 helper） |
| 主线程取颜色 | 10.9 s | 0（在出图线程里，6.9 到 7.4 s 摊给 6 个线程） |
| 主线程空等出图 | 1.2 / 1.8 s | 5.8 s |
| 走了 Pillow 的照片 | 500 | 0 |

- 这一批 HEIC 是 sips 编的，Pillow 解它比解 pillow-heif 编的快，所以 `main` 只要 14 秒（§1.1 是 21 秒），主线程取颜色（10.9 秒）已经比出图还慢：第 1 步的收益在这里显出来了。
- 同样 500 张，CPU 只用原来的三分之一：风扇和电池都轻得多。
- 一致性（同一批照片，两边的图库逐张比）：
  - 显示形状（横 / 竖 / 方）、缩略图状态：500 张完全一致。
  - 相似照片哈希：中位数 0 位，最大 4 位（判重阈值 8，「相似」阈值 20）。
  - 调色板：按占比加权的色差中位数 4.0 ΔE，95% 的照片在 6.9 以内，最大 8.1；颜色筛选最严一档的容差是 15。拿一组 Lab 网格上的颜色去筛，结果变了 2.1%，都在容差边上。对照：Pillow 自己从 JPEG 质量 90 换到 85，样片上是中位数 3.5 ΔE、变 1.8%，量级相同。
  - 缩略图目录 23 MB → 25 MB。
- 主线程现在有 5.8 秒在等出图，出图线程的 27 秒里大半是在等 helper 回复。再往下压要加 helper 进程，或者把颜色和哈希挪进 helper，这次没做。

### 1.8 第 5、6 步之后（人脸多 worker、重新导入先比对）

又一批用 `--sips` 生成的 500 张，先用 `main` 导入一次，再把图库拷成几份分别测。原始输出在 `results-2026-11-26/step5-*.json`、`step6-*.json`。

| | `main` | 分支 |
|---|---|---|
| 人脸分析 500 张 | 115.6 s（1 个 worker） | **42.9 / 46.8 s**（3 个 worker），108.5 s（同一分支限定 1 个） |
| 人脸分析的 CPU 合计 | 115 s | 112 到 120 s |
| 每个 worker 的内存（峰值） | 1.6 到 2.5 GB | 1.0 到 1.4 GB，3 个合计约 4.2 GB |
| 重新导入 500 张没变的照片 | 1.88 s，CPU 4.0 s，ExifTool 读 500 次 | **0.15 s**，CPU 0.1 s，一次不读 |

- 人脸快了 2.5 到 2.7 倍，CPU 总量不变：活一样多，只是摊到了 3 个核上。两边 500 张都分析完（这批是风景照，没有人脸，检测的成本照付）；`62-people-real-model` 用真模型、3 个 worker 跑过，分组结果和以前一样。
- 内存是代价：worker 一开始就占到 1 GB 以上，之后上下浮动，不是越积越多（给每张照片套 `autoreleasepool` 试过，峰值在噪声范围内，没有保留）。3 个 worker 比 1 个多占约 2 GB，这就是「每 6 GB 内存一个」那条限制的用处：8 GB 的 Mac 仍然只开 1 个。
- 重新导入快了 12 倍，和文件夹大小成正比，放在网络盘上省得更多。

## 2. 目标

- 同样 500 张，导入（能在画廊里看到、能按颜色筛选、能找相似）从 21 秒降到 8 秒以内（Mac）。
- 打开了「导入后识别人脸」时，导入加人脸从 135 秒降到 60 秒以内。
- 导入被取消、失败，或者导入中途退出 App，已经导进来的照片照样会做完设置里打开的后续分析。
- 后台任务之间有明确的先后，不再同时抢 CPU。
- 缩略图、颜色、相似照片、方向的结果和现在一致（§7）。

**非目标**：不改索引和 RAW 匹配的逻辑；不改 HD 和 RAW HD 的按需生成；Windows 的出图引擎这次不换。

## 3. 新管线一览

```
发现（走一遍目录，没变的文件直接跳过）
  → 索引（不变）
  → 出图：一次解码，在工作进程或线程里算完缩略图、特征向量、颜色、方向；主线程只写库
     Mac：常驻的 ImageIO helper 进程池；Windows 和 ImageIO 读不了的格式：Pillow（现在的路径）
导入结束（成功、取消或失败，只要有新照片）
  → 主进程的协调器，按设置排后续任务
     分析道：人脸（多个 worker）、颜色 / 相似照片 / 方向补漏，一次一个，导入在跑时等待
     网络道：AI 标注，不占 CPU，可以和别的任务同时跑
```

## 4. 出图

### 4.1 Mac：ImageIO helper 进程池（已实现）

做成的样子（`native/image-features.swift` 的 `thumb` 请求，`services/sidecar/src/media_workspace/image_io_previews.py`）：

- **没有新做一个可执行文件**，给现有的 `image-features` 加了一种请求 `{"op":"thumb", …}`。打包、签名、`IMAGE_FEATURES_PATH`、macOS 12 和 Intel 的构建都不用动。只出缩略图的 helper 进程从不做特征向量，也就不加载 Vision 的模型。
- 每个出图线程借一个 helper 进程，进程常驻、批次之间复用，退出时关掉（`HelperPool`，和特征向量那一组分开：太慢、不做特征向量的 Mac 照样用它出图）。
- 只接 **JPEG 和 HEIF**，而且只接 8 位 RGB、不带透明的；CMYK、灰度、透明、每通道超过 8 位（相机的 10 位 HDR HEIF）都回复「不接」，照旧走 Pillow。PNG、TIFF、WebP、AVIF 不经过 helper：它们很少见，Pillow 也不慢，接过来要逐种对齐 Pillow 的转换，不值。
- **缩略图和 Pillow 出的一致**，规则都由 Python 按 Pillow 读到的文件头定，再交给 helper：
  - JPEG 像素按原样存，写 Pillow 读到的方向标签；
  - HEIF 像素转正、不写标签，因为 pillow-heif 交出来的就是转正的（libheif 会应用 irot）；pillow-heif 保留了方向标签的少数 HEIF 交给 Pillow；
  - 尺寸按 Pillow 的取整规则精确到像素（`pillow_preview_size`）。ImageIO 的短边向下取整，5997×6000 会变成 511×512 的「竖图」，Pillow 是 512×512 的「方图」。差 1 像素时 helper 重绘一次；
  - 保留 RGB 色彩配置（P3、Adobe RGB 照旧）；不放大小图。
- JPEG 质量取 ImageIO 的 0.8。它的刻度和 libjpeg 不同：画质最接近 Pillow 的 90，文件大约大一成。
- **回退**：没有 helper（Windows）、helper 是这次改动以前编的（`--thumb-protocol` 答不出 1）、超时 30 秒、进程退出、stdout 上出现协议外的行（#215 那种）、ImageIO 读不了，都回到 Pillow，再不行回到 sips。以前能出图的文件不会出不来。
- 原计划「在 helper 里用同一张内存里的图算特征向量」没做：相似照片的测量在出图线程里只占 3.3 秒（各线程相加），合进来要改特征向量的输入（内存里的图和读回来的 JPEG 不完全一样），不值。

### 4.2 颜色和感知哈希挪到工作线程

现在相似照片的测量已经在出图线程里做（`render_and_measure`），主线程只写结果。颜色照同样的方式做：出图线程算出调色板（`colors.extract_palette`），主线程只调 `replace_asset_colors`。感知哈希仍在 Python 里从缩略图算，同样放在工作线程。

这一步不依赖 4.1，可以先做；Windows 也受益。

### 4.3 Windows

保持 Pillow。HEIC 在 Windows 上同样慢，但先要在 Windows 开发机上测一次（`pillow_heif` 的解码线程数、WIC），再决定，不在这次范围里。

## 5. 后续任务交给主进程

### 5.1 协调器

新建 `electron/pipeline.js`，接手现在散在渲染层的三件事：

| 现在在哪 | 做什么 |
|---|---|
| `App.jsx` `onJobFinished` | 导入成功后按开关起标注、人脸 |
| `App.jsx` `useCatalogCatchUp` | 打开图库时补颜色、相似照片、方向 |
| `tasks.js` 的 `latestJobStatus(...).running` 判断 | 同一类任务只跑一个 |

渲染层只负责显示，任务列表照旧从 `list-active-jobs` 读。

### 5.2 什么时候触发

- `launchSidecarJob` 本来就监听 runner 进程退出。导入任务退出时，读一下它的任务行：只要 `newly_added > 0`，不论成功、取消还是失败，都按两个开关（自动标注、导入后识别人脸）排后续任务（已拍板）。
- 排上的后续任务记在导入任务的结果里（`result.followups`，比如 `{"people": "queued", "annotation": "queued"}`），起了就改成 `started`。
- 启动时扫一遍最近的导入任务，`followups` 里还有没起的就补起。这样导入中途退出 App 也不会漏。

**标注只标这次导入的照片**（已拍板，行为变化）。现在导入成功后标的是整个图库里还没标注的照片（`App.jsx` 的 `runAnnotation(null, { scope: "all", onlyMissing: true })`）：第一次打开开关时库里有 1 万张没标注的旧照片，导入 5 张也会把 1 万张一起标掉，事先没有提示。改成只标这次导入新增的照片，花多少钱和导入了多少张对得上；旧照片照旧在设置里手动点「标注未标注的」。

- 圈定范围不改 schema：标注任务加一种范围 `import`，带导入任务的 id。sidecar 取那次导入的时间窗（任务行的 `created_at` 到退出时的 `updated_at`）和导入目录，选 `assets.created_at` 落在窗内、`canonical_path` 在这些目录下的照片，再叠加现有的「只标没标过的」。`assets.created_at` 只在第一次插入时写（`db/assets.py` 里 `_upsert_asset_row` 的 `ON CONFLICT` 不碰它），所以重新导入、认回移走的照片都不算新的。
- 两边都是 SQLite 的 `CURRENT_TIMESTAMP`，同一格式、精确到秒，可以直接按字符串比较。窗口内别的途径写进同一目录的新照片（比如导出到原图旁边）也会被算进来，可以接受。
- 人脸不改范围：它本来就跳过已经识别过的照片，不花钱，整个图库补齐是对的。

### 5.3 两条道，取代 `priority`

| 道 | 任务 | 规则 |
|---|---|---|
| 导入道 | 导入 | 一次一个（不变） |
| 分析道 | 人脸、颜色 / 相似照片 / 方向补漏、批量 HD | 一次一个；导入在跑时等它结束 |
| 网络道 | AI 标注、重绘、手写字 | 一次一个，不受另外两条道影响 |

- 每条道里先到先跑，用户手动点的排在自动触发的前面。只有这两档，不再写数字优先级。
- 排着的任务照旧写成 `queued` 的任务行，活动中心本来就会显示。
- `jobs.priority` 列保留（不动 schema），只存「用户 / 自动」两档；`list_active_jobs` 的排序改成按道和先后。
- **已经在跑的人脸任务遇上导入：暂停，导入完自动续跑**（已拍板）。人脸任务本来就支持在照片之间暂停、按游标续跑（`job_runner.py` 的 `_check_pause` / `_mark_people_paused`），协调器直接用：导入开始时对它发暂停请求，并在结果里记 `paused_by: "import"`；导入道空了以后只续跑这样暂停的任务，用户自己点暂停的照旧停着。颜色 / 相似照片 / 方向补漏都很短，让它跑完，不打断。
- 依据：导入时平均有 5.4 到 6.7 个核在忙（分别是 6 个和 12 个出图线程），每个人脸 worker 还要再占 1 个核。两者同时跑会拖慢多少没有实测，第 4 步动手前先测；要是测出来几乎不拖慢，再回头考虑让人脸降到 1 个 worker 接着跑。

### 5.4 导入排队挪进主进程

渲染层的 `pendingImport` 队列挪进协调器（已拍板，放在最后一步单独做）。MCP 的 `import_directory` 撞上正在跑的导入时改为排队，不再报错（评估 2026-09-16 那条）；这改了 MCP 现有的行为，PR 里要写明，`docs/agent-native-mcp.md` 里这个工具的说明同步改。

## 6. 人脸：多 worker

- `run_people_index_job` 同时开 N 个 people-worker 进程，把候选照片分给空闲的 worker；所有写库仍在 sidecar 主线程，按照片为单位提交（不变）。
- N：分析道单独跑时取 `min(3, 核数 / 4)`（M3 Pro 上 3 个）。导入在跑时分析道本来就在等，所以不用再动态调整。
- 断点续跑：现在的游标是「做到第几张」。并发以后完成顺序是乱的，游标改记「连续做完的最后一张」；续跑时它后面已经做完的照片会再做一次。写入是按照片整体替换的（`replace_asset_faces`），重做无害。
- 预期：2 个 worker 实测 1.82 倍，3 个按此外推约 2.5 倍，114 秒降到约 45 秒。
- 不在这次范围：分析分辨率（现在长边最多 4096）。降下来会快，但小脸可能检测不到，要先用 portrait.afcatalog 那套验证配方测召回率。

## 7. 结果一致性

| 结果 | 风险 | 怎么保证 |
|---|---|---|
| 缩略图 | ImageIO 的缩放算法和 Pillow 的 LANCZOS 不同，画面会有细微差别 | 不重做已有的缩略图；方向、尺寸、色彩配置、不放大各有单测（`tests/test_image_io_previews.py`） |
| 颜色 | 调色板来自缩略图，换了缩放算法会有偏差 | 实测（§1.7）中位数 4.0 ΔE、最大 8.1，和 Pillow 自己换个 JPEG 质量同一量级，远小于筛选容差 15，所以**不标 stale、不重做** |
| 相似照片 | 新旧缩略图混在一起，哈希会有偏差 | 实测最大 4 位，判重阈值 8；`78-lookalikes.spec.js` 通过 |
| 方向 | 尺寸取整不同会让接近正方形的照片换类 | 尺寸按 Pillow 的规则对齐（§4.1）；实测 500 张显示形状完全一致 |

## 8. 小修

- **重新导入时先比对再读**：先 stat，路径、大小、修改时间都和库里一致的文件不再读 EXIF 和算指纹。本地每张只省 2.2 ms，但它和文件夹大小成正比，5 万张的文件夹放在 NAS 上可能就是几分钟到十几分钟。要保留 `refresh=True` 时「有新 RAW 源就重新打分」的作用，用库里存的元数据打分。
- **目录只走一遍**：`sorted(rglob)` 本来就把整个列表放进了内存，直接用它的长度当总数。本地可以忽略，NAS 上省一遍 stat。

## 9. 不做的

- 索引和出图并行：索引只占 4%，最多省 0.8 秒。
- 索引阶段合并提交：本地 500 次提交共 0.08 秒。图库放在网络盘上的情况没测，真有人报慢再说。
- 加出图线程：§1.2，12 个线程只快 9%。

## 10. 分几步做

原计划每一步单独一个分支。实际按「一个分支一件事、不叠分支」合成了四个，各自从 `main` 开，互不依赖：第 1 步单独合并会变慢（§1.6），和第 2 步放在一起；第 4、7 步都建在第 3 步的协调器上。

| | 内容 | 分支 | 实测 | 跑过的 e2e |
|---|---|---|---|---|
| 1、2 | 颜色挪到出图线程；Mac 上 JPEG、HEIF 走 ImageIO（§4） | `perf/import-colors-in-threads` | 导入 14 s → 7.4 s，CPU 降到三分之一（§1.7） | `52`、`78-lookalikes`、`37`、`35`、`64`、`65` |
| 3、4、7 | 主进程协调器：导入结束（含取消、失败）后的后续任务、标注只标这次导入的、导入时人脸让路、MCP 导入排队、优先级两档（§5） | `feat/import-followups-coordinator` | 行为变化，没有耗时数字 | 新增 `103-import-followups`（5 条），加 `11`、`08`、`36`、`10`、`17`、`62`、`71`、`72`、`52`、`78`、`65` |
| 5 | 人脸多 worker（§6） | `perf/people-index-workers` | 115.6 s → 42.9 到 46.8 s（§1.8） | `62`、`71`、`72` |
| 6 | 重新导入先比对、目录只走一遍（§8） | `perf/reimport-stat-first` | 重新导入 1.88 s → 0.15 s（§1.8） | `17`、`64`、`11`、`81`、`94`、`35` |

和方案有出入的地方：
- 第 3 步原计划的 e2e「取消导入后照样识别人脸」改成了「取消导入后照样标注」：两者走同一套后续机制，标注能数清发了几个请求；人脸后续的规则在 `electron/pipeline.test.js` 里测。
- 第 7 步没有把渲染层的 `pendingImport` 整个搬过去：它还管着「导入完放进文件夹」和导入模式的判定。主进程另有一个队列，接住渲染层以外的导入（MCP、内置样片）。MCP 撞车时改为排队这一条做到了。
- 第 4 步的「两条道」落成了：导入在跑时人脸暂停（导入期间你手动点继续的，这次导入里不再被暂停），自动发起的颜色 / 相似照片 / 方向补漏和导入后的批量 HD 推到导入之后（你在设置里点的、agent 调用的照常立刻跑）；网络道（标注、重绘、手写字）照旧各管各的。导入和人脸同时跑会拖慢多少，没有再单独测：既然人脸会暂停，这个数字已经不影响设计。
- 顺手修的：暂停中的任务点「取消」以前只是打标记，没有进程处理它，会一直显示「正在取消」。现在暂停中的任务取消即生效（导入期间开始的人脸分析一开始就是暂停的，更容易碰上）。

要在 PR 里写明的行为变化：Mac 上缩略图换了生成方式，文件约大一成（第 2 步）；导入后自动分析在取消、失败后也会触发，自动标注只标这次导入的照片（第 3 步）；导入时人脸分析会暂停，补漏任务推到导入之后（第 4 步）；MCP `import_directory` 撞车时排队而不是报错（第 7 步）；重新导入不再重读没变的文件（第 6 步）；人脸分析期间内存多占约 2 GB（第 5 步）。

## 11. 已拍板（2026-11-26）

1. 导入失败时也触发后续分析，只要这次有新照片（§5.2）。
2. 导入后自动标注只标这次导入新增的照片，不再标整个图库里没标注的（§5.2）。这一条是排查第 1 条时发现的，原方案没写。
3. 导入在跑时，已经在跑的人脸任务暂停，导入完自动续跑；不降到 1 个 worker（§5.3）。第 4 步前的实测要是推翻这个依据，再回来议。
4. 导入排队挪进主进程，作为第 7 步单独做（§5.4）。
