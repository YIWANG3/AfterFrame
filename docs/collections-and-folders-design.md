# 合集与文件夹：虚拟归属和磁盘镜像分开

> **状态（2026-11-18）**：第 0 到第 3 阶段已实现，合在一个分支、一个 PR 里（用户要求做完再开 PR，不按第 8 节分开提）。第 9 节的 7 项已全部拍板。
>
> 实现与下文的差异和补充：
> - 文件夹作为「位置」走现成的 `base`：渲染层作用域多一个 `folderPath`，请求带 `base = {status: "all", filters: {in_folder, in_folder_descendants}}`（`workspaceLogic.folderBase`）。sidecar 新 facet `in_folder`（`db/facets.py`，条件在 `db/folders.py folder_clause`），智能合集的规则不收它（`smart_rules._SAVABLE_FILTER_KEYS`），在文件夹里也不显示「存为智能合集」。浏览、计数、筛选项、地图、按清单找图都因此直接按文件夹生效。
> - 目录树：`list-folders`（`db/folders.py list_folders`），以图库「全部素材」能看到的照片为准（合并的 RAW 不单独算）。每个卷从根往下折叠「本身没照片、只有一个子目录」的祖先。
> - 定位：`locate-folder`（`locate_folder`），按前缀换路径、逐张走 `relink_asset`；被合并的 RAW 跟着接回但不计数。
> - 同步：`verify-assets --under <dir>` 加上 `auto` 导入（导入时自动认领挪动的文件）。
> - 自动同步：监视器（`electron/watcher.js`）现在处理消失：文件不见了按路径校验（`verify-assets --path`），目录不见了按目录校验，有新缺失时发 `workspace:catalog-changed`（reason `watcher`）让界面刷新。整个目录挪进来（只报目录、不报里面文件）时按目录导入；新建的空文件夹、和里面文件一起报上来的父目录不导入。
> - 「保持同步」按钮复用了原来的「监控这个文件夹？」提示（任何手动导入文件夹都会弹，不只是拖到文件夹区），文案改成同步。设置里的「监控目录」改叫「自动同步的文件夹」。
> - 「存为合集」用的是新建合集的现成入口，所以新合集也会成为 B 键的目标合集（新建合集一直如此）。
> - 合集行的图标换成相册（Album），文件夹图标只用于磁盘文件夹。

## 1. 问题

现在应用里的「文件夹」是 `collections` 表里 `kind = 'manual'` 的行，纯虚拟：照片先在图库里，文件夹只记归属（`collection_items`，按 `asset_id`）。这条原则没有问题，问题出在三处后来加的入口都在暗示「文件夹 = 磁盘目录」：

1. **从访达拖入文件夹**（#277）会建一个同名的 app 文件夹，「保留子文件夹」（#298，`collection-add-paths --mirror`）还会把磁盘结构逐层建出来。导入结束后两者就没有关系了，但用户看到的是一棵跟磁盘一模一样的树。
2. **名字本身。** 「文件夹」在 macOS 上就是磁盘目录。同一个词在文案里两种意思都有：侧栏的「文件夹」是虚拟的，「从文件夹全部找回…」「导入文件夹…」里的是磁盘的。
3. **用户在访达里挪了目录之后**，会自然地问：App 里的文件夹要不要跟着变？反过来，在 App 里挪了一个「镜像出来的」子文件夹，磁盘要不要动？

如果在现有「文件夹」上加一个「自动同步」开关，让一部分文件夹跟着磁盘走，同一个列表里就有了两套规则：能不能手动加照片、移出的照片下次同步会不会回来、两类能不能互相嵌套、删除时给什么选项。每个操作都要先问「这是哪一类」，用户记不住。

## 2. 结论

拆成两个概念，各自只有一套规则：

| | **合集** | **文件夹** |
|---|---|---|
| 是什么 | 归属，纯虚拟 | 磁盘目录的只读镜像 |
| 数据 | `collections` / `collection_items`（不变） | 由照片原文件路径推出，不存树 |
| 结构怎么变 | 只由用户在 App 里整理 | 只跟着磁盘变（访达 → App，单向） |
| 手动加入或移出照片 | 能 | 不能，要整理就去访达 |
| 新建、改名、移动、嵌套 | 能 | 不能 |
| 删除 | 现在的三选一 | 从图库移除 / 移到废纸篓，见 §5.4 |
| 智能合集 | 合集的一种，用图标区分 | 无 |

- 现在所有的手动文件夹都改名为**合集**，数据不动。「智能合集」本来就叫合集，命名反而统一了。
- **文件夹**是新增的面板，展示图库里照片所在的磁盘目录。
- 两者之间**没有同步**，只有显式、一次性的转换（§6）。

与 Capture One 的区别：它的 Folders 是双向的，在 App 里挪文件夹会真的移动磁盘文件。我们的文件夹只读，不提供任何改动磁盘结构的操作，所以「照片在三个合集里，磁盘上放哪」「两边都改了听谁的」这类问题不会出现。

## 3. 非目标

- 在 App 里移动、改名磁盘目录或文件。真要整理磁盘，以后单独做「拷贝到磁盘目录…」，性质跟导出一样，一次性、单向。
- 合集跟着磁盘变。合集永远只由用户整理。
- 改数据库里 `collections` 的表名、`kind` 取值或 MCP 的 `collection_id` 参数名。改名只发生在界面文案和工具描述里。

## 4. 合集（原「文件夹」）

行为完全不变，只换名字和入口文案：

- 侧栏从上到下三个并列的区：「智能合集」「合集」（原来的「文件夹」，英文 Collections）「文件夹」（磁盘）。每区只有自己的行那么高，从上往下排，空白留在底部；智能合集最多占侧栏 40%，合集和文件夹各最多 45%，超出在区内滚动，三区加起来放不下时整个侧栏滚动。（2026-11-19 用户改定，原来是一个合集区内分「手动」「智能」两组。）
- 文件夹页（`FoldersView.jsx`）→ 合集页；「目标文件夹」（B 键）→ 「目标合集」；「加入文件夹」→ 「加入合集」；「含子文件夹」开关 → 「含子合集」。
- 图标：手动合集一个图标，智能合集保留现在的图标，一眼能分开。
- 删除三选一（只删合集 / 从图库移除 / 移到废纸篓）不变。
- 从访达拖到**合集区**：维持现在的行为（导入 + 建合集，有子目录时问拍平还是保留）。弹窗里的「保留子文件夹」改叫「按子文件夹分组」，「全部放进一个文件夹」改叫「全部放进一个合集」。
- 合集详情里不显示任何磁盘路径，避免暗示绑定。
- **侧栏可自定义**（2026-11-19）：除「全部素材」外，侧栏每一项（最近添加、已评分、近似重复、发现、贴纸、人物、标签、统计，以及三个区）都能隐藏。入口是右键菜单里的「在侧栏隐藏」和各区「⋯」里的「在侧栏隐藏」；设置 › 通用 › 侧栏 列出所有项，每项一个开关（`components/sidebarLayout.js`，偏好 `sidebar.hidden`）。只做显示和隐藏，不做排序。
- **三个区的标题工具统一**为「搜索、＋、⋯」：智能合集是 ＋（回到全部素材、打开筛选栏，设好条件后存）和 ⋯（列表/封面、在管理页打开、隐藏）；合集是搜索、＋ 新建、⋯（排序、列表/封面、在管理页打开、隐藏）；文件夹是搜索、＋ 导入文件夹、⋯（按名称或张数排序、全部同步、在管理页打开、隐藏）。智能合集区没有内容时也显示，写「暂无智能合集」。文件夹的计数始终含子目录。
- **管理页三个标签**：智能合集 / 合集 / 文件夹，替代原来的标题；从某区的「在管理页打开」进来落在对应标签。合集标签就是原来的合集页；智能合集和文件夹各是一页卡片或列表（`components/ManagerPages.jsx`），可搜索、排序，右键菜单和侧栏一致。

## 5. 文件夹（新增）

### 5.1 树从哪来

不新建表。树由图库里每张照片的原文件路径推出：

- 取所有在库照片（图片、视频、未配对的 RAW；配对的 RAW 跟着它的 JPG，不单独算）的 `dirname`，按目录聚合出每个节点的「直接照片数」。
- **顶层怎么切**：先按卷分组（本机、各个外接盘，用卷名而不是 `/Volumes/xxx`），卷内把只有一个子目录、自己又不含照片的祖先链折叠掉。例如照片都在 `/Users/me/Pictures/2024/…` 下，顶层直接显示 `2024`，悬停显示完整路径。
- 计数沿用「含子文件夹」开关：默认显示含子目录的总数。
- 只出现含照片的目录（含子孙）。空目录不显示，这是图库的镜像，不是访达。

`image_lookup_registry.image_path` 是主键，前缀查询（`image_path >= 'dir/' AND image_path < 'dir0'`）可以走索引；`assets.canonical_path` 目前没有索引，第 2 阶段视查询方式决定要不要加（加索引需要迁移，见 §7）。路径大小写：macOS 默认卷和 Windows 不区分大小写，比较时按卷的规则来，第一版先统一按不区分大小写处理。

### 5.2 浏览

- 点一个文件夹 = 换「位置」（两层筛选模型里的位置层，走 `goTo()` 唯一入口），网格显示这个目录（可含子目录）里的照片，细化筛选照常可用。
- 照片详情（检查器、灯箱详情栏）显示「文件夹」一行：磁盘路径，点击跳到该文件夹；下面另列它所在的合集。
- 在访达中显示。

### 5.3 缺失

- 目录不在了：文件夹显示为**丢失**，右键「定位…」。
- 外接盘拔掉**不单独区分**，维持现在的行为：`verify_assets` 只看 `os.path.exists`，拔盘后那些照片算缺失、进缺失原文件视图，对应的文件夹显示为丢失。插回来后，校验文件或浏览时的懒校验会把它们恢复。不引入「离线」状态。

### 5.4 文件夹上能做的操作

| 操作 | 说明 |
|---|---|
| 定位… | 目录被挪走后，指给它新位置。把该目录下所有照片的路径按前缀从旧目录换到新目录，每张都校验指纹（`relink_asset` 的规则，不强制），结果按「接回 / 没找到 / 同名但内容不同 / 已被另一条记录占用」汇报。这就是 C1 的 Locate、Lightroom 的「找到丢失的文件夹」。 |
| 同步 | 扫一遍这个目录：新文件导入、不在了的标缺失、挪动的自动认领（§5.5）。未开启自动同步的文件夹靠这个手动刷新。 |
| 自动同步 开 / 关 | 见 §5.6。 |
| 存为合集… | 一次性快照，见 §6。 |
| 在访达中显示 | |
| 从图库移除… | 针对这个目录（含子目录）下的所有照片，确认框里两项，和合集删除一致：「从图库移除」（说明评分、标签、合集归属会一起没掉，文件留在磁盘）和「移到废纸篓」（沿用单张照片的做法：只移 image_path，配对 RAW 不动）。确认框写明张数和目录路径。 |

**不能做**：新建、改名、移动、拖照片进来、从文件夹里单独「移出」某张照片（只能从图库移除）。照片拖到文件夹节点上不是有效的放置目标。

### 5.5 前置能力：导入时自动认领

这是第 0 阶段，独立于改名也有价值，文件夹的同步依赖它。

现在图片的 `asset_id` 由「指纹 + 路径」算出（`metadata.py stable_asset_id`）。挪过的文件重新导入时会生成一条新记录，旧记录留在缺失视图里，评分、标签、合集归属都在旧记录上；之后再批量找回，只会得到 `in_use`。

改为：导入一个新路径时，如果库里有**同类型、同指纹、原路径已经不存在**（导入时现场 `stat`，不依赖 `exists_on_disk` 标记，避免和监视器的删除事件抢先后）的记录，就把那条旧记录接到新路径上（`relink_asset`），不建新记录。

- 候选不止一条（同一张图有过几份副本）：先比文件名，唯一命中才认领，否则照常新建，不猜。
- 配对的 RAW 一起认领：JPG 被认领时，它配对的 RAW 如果也缺失，按同样的规则在新位置找。顺便修掉批量找回的同一个问题：`useMissingFiles` 只把图片 id 传给 `relink-from-folder`，配对的 RAW 不会跟着接回。
- 导入结束的提示里加一句「其中 N 张是之前缺失的照片，已接回原来的记录」。
- 这改变了既有的导入行为（以前会新建记录），PR 里要写明。

### 5.6 自动同步

**自动同步的文件夹 = 现在的监视文件夹**（`integrations.watchedDirs`，`electron/watcher.js`）。两个概念合并，不再并存：

- 设置里「监视文件夹」那一栏改为「自动同步的文件夹」，和文件夹面板右键的开关是同一份数据。
- 监视器现在只处理新增和覆盖写入，删除事件直接丢掉（`watcher.js` 「keep what exists」）。要补上：路径消失 → 标缺失；同一批里新路径出现 → 按 §5.5 认领。这样在同步文件夹里挪动、改名目录，App 不用任何操作就跟上了。
- 没开自动同步的文件夹：靠右键「同步」或现有的「文件 › 校验文件」。
- 监视文件夹仍然**只是导入来源**，不往任何合集里归档，否则它就成了一条隐形的同步通道。

从访达拖到**文件夹区**：导入，目录自然出现在文件夹树里，不建合集。**默认不开启自动同步**（外接大盘全量监视有成本）；导入完成的提示里带一个「保持同步」按钮，点了就把这个目录加进自动同步，之后也能在文件夹右键里开关。

## 6. 两者之间的桥

只有显式、一次性的转换，没有同步：

- **存为合集…**（文件夹右键）：把当前目录（可选含子目录、按子目录分组）建成一个合集，之后两者无关。等价于现在的「拖到合集区 + 保留子文件夹」，只是不用再拖一次。

**不做**跟着文件夹走的智能合集（智能合集规则里加「在文件夹 X 下」的前缀条件）。不存在「会跟着磁盘变的合集」，两个概念的边界保持干净。筛选栏现有的 `path_contains`（路径子串）不受影响。

## 7. 迁移与对现有用户的影响

- **数据**：第 1 阶段不动数据库，不升 schema。第 2 阶段如果要给 `assets.canonical_path` 加索引，走 `db/migrations.py`，`SCHEMA_VERSION` 15 → 16，按 CONTRIBUTING 的「Easy to break」处理 schema 和提交的 fixture。
- **升级后**：用户原来的「文件夹」全部出现在「合集」里，内容、嵌套、顺序都不变。文件夹面板从现有照片路径推出，**一升级就有内容**，不是一个空的新概念。
- **文案**：zh-CN 里「文件夹」约 70 处（nav 55、app 10、settings 4、collage 2、editor 2），en 同量。逐条区分：指虚拟归属的改为「合集 / Collection」，指磁盘目录的保留。不能全局替换。
- **设置项**：目标合集、含子合集等偏好的存储键不改，只改标签。
- **MCP**：`manage_collections`、`search_assets` 的 `collection_id` / `include_descendants` 描述里的「folder」改为「collection」；server instructions 里 "a folder is a manual album" 改写；第 2 阶段新增按磁盘文件夹筛选（`search_assets` 加 `folder` 前缀参数，或新工具 `list_folders`），同步更新 `docs/agent-native-mcp.md`。
- **e2e**：约 40 个 spec 提到 folder / 文件夹，多数用文字定位。第 1 阶段要逐个改选择器，这是改名阶段的主要工作量。
- **官网、README、截图**：工作区里正在更新的 folders、folders-page 截图会过时。最好在这批素材发出去之前定下第 9 节的命名，否则要重拍。
- **发版说明**：明确写「文件夹改名为合集，新增按磁盘目录浏览的文件夹」。

## 9. 已定决策（2026-11-18）

1. **英文名**：Collection / Folder（中文：合集 / 文件夹）。和现有的 Smart Collection 统一。
2. **侧栏排布**：~~一个「合集」区，区内分「手动」「智能」两组~~。2026-11-19 改为三个并列的区：智能合集、合集、文件夹，分割更清楚；各区按内容高度从上往下排（§4）。
3. **文件夹顶层**：按卷分组 + 折叠单链祖先，只看路径推导，不依赖 `catalog_roots`（§5.1）。
4. **拖到文件夹区**：默认不开自动同步，导入完成的提示里给「保持同步」按钮（§5.6）。
5. **文件夹的删除**：带「移到废纸篓」，和合集删除一致（§5.4）。
6. **拔掉的外接盘**：维持现状，算缺失，不引入「离线」状态（§5.3）。
7. **跟着文件夹走的智能合集**：不做（§6）。
