# 导入管线评估（2026-11-26）

范围：从「选文件夹 / 拖进来 / 监视文件夹 / MCP」到缩略图、颜色、相似照片、方向、AI 标注、人脸识别全部做完的整条链路。
方法：先读代码，同日又实测了一次（500 张 24 MP JPEG + 12 MP HEIC，M3 Pro，热缓存，数据见 [import-pipeline-redesign.md §1](../import-pipeline-redesign.md)）。实测推翻了读代码时对吞吐的几条猜测（3、6），也找出了读代码没看出来的三处真正的大头（8 到 10）。重新设计的方案在 [import-pipeline-redesign.md](../import-pipeline-redesign.md)。
行号以 `feat/collections-and-folders`（edf743ed）为准，会漂移，以函数名定位。

## 现状

### 1. 入口

手动导入、拖到画廊或程序坞、监视文件夹（实时 + 启动时补漏）、MCP `import_directory`、内置样片，全部走 `electron/tasks.js` 的 `startImportTask`：
写一行 `jobs`，再起一个独立的 sidecar 进程 `run-import-job`（`launchSidecarJob`，detached）。同一时间只跑一个导入，撞上时 UI 排队（`pendingImport`），MCP 报错。

监视文件夹和启动补漏在发起导入前，先让 sidecar 过滤掉库里已有且没变的文件（`watcher.js` 文件头、`ipc/assets.js` 的补漏检查），所以它们只导入真正新的文件。

### 2. 导入任务（`job_runner.run_import_job`）

按模式拼阶段（`_build_import_phases`），常见的「导入图片文件夹」是：

1. **索引**（`reverse_lookup.resolve_image_batch`）：先把目录走一遍数总数，再走一遍逐个处理。每个文件：
   ExifTool 读元数据（常驻进程池，提前读后面 4 个）→ 头尾指纹 → 写 asset → 匹配 RAW（SQL 召回 + 打分）→ RAW+JPG 配对 → 每个文件提交一次。
2. **边索引边出图**：每满 100 张或 8 秒，停下索引，把这批交给 `PreviewService.generate_batch` 出 512 缩略图（CPU 核数一半的线程），出完再接着索引。画廊因此是一批批填满的（#130）。
3. **缩略图补漏**：索引完再对整个目录过一遍图片、视频封面、RAW 缩略图，只做前面漏掉或失败的；内容变了的文件刷新已有的 HD 预览。
4. **HD 预览**（2000px）：默认关，设置里开了才有这一步。RAW 的 HD 用到时再生成。

### 3. 出缩略图时顺带做的

缩略图解码一次，顺带算出：主色（`colors.analyze_asset_colors`，写库线程上做）、相似照片的哈希和 Mac 上的特征向量（渲染线程里做）、横竖方向。所以导入完时这三样已经有了。

### 4. 导入完以后（渲染层 `App.jsx` 的 `onJobFinished`）

只在导入**成功**时：

- 开了「导入后自动标注」→ 起标注任务（LLM，默认 3 个并发请求，设置里可改；发 512px 图）。
- 开了「导入后识别人脸」且模型可用 → 起人脸任务（Swift Core ML worker，读原图，可断点续跑）。

两个开关默认都关。

### 5. 打开图库时补漏（`App.jsx` 的 `useCatalogCatchUp`）

颜色、相似照片、方向各一个任务，没活就不起任务，起了的用 `nice(5)` 降优先级。

## 做得好的地方

- **解码一次，多处复用**：颜色、相似照片、方向都从同一张缩略图里取，不再各读一遍原图。这是这条管线里最值钱的设计。
- **贵的层级不预先做**：HD 默认关，RAW 的 HD 按需生成，AI 两步默认关、开了也排在导入之后。导入完图库马上能用。
- **分批出图**：大盘导入时画廊不会一直空着。
- **任务状态以数据库为准**：每个任务独立进程、进度写库，渲染层重载不影响；进度写入有节流（`_ProgressGate`）、可取消、心跳超时回收、进程提前退出会标失败。
- **锁的教训都落实了**：慢的读文件不放在写事务里，缩略图结果攒一批再提交，避免 0.5.8 那种「database is locked」。
- **边界情况考虑得全**：半写完的导出先跳过（`validate_source_ready`），删掉的文件不会被自动导入复活（tombstone），移走再放回的文件认回原记录，预览先写临时文件再原子替换。

## 问题

1 到 7 是读代码时列的，8 到 10 是实测以后补的，11 是拍板时发现的。按实测，影响最大的是 8 和 10，先后顺序见文末。

- [ ] **1. 导入后的 AI 步骤挂在渲染层，而且只认「成功」** · CONFIRMED
  `App.jsx:558` 的分支条件是 `fin.jobType === "import" && fin.status === "succeeded"`。导入到一半被取消（已索引的照片保留）或失败，这些照片不会自动标注、不会识别人脸；导入时退出 App 也一样，下次启动没有补漏（`useCatalogCatchUp` 只管颜色、相似照片、方向）。要等下一次成功的导入，它们才会被顺带补上。
  另外「导入完该做什么」是 UI 组件里的副作用，主进程和 MCP 看不到这条规则。
  修法：挪到主进程。`launchSidecarJob` 本来就在监听 runner 进程退出，退出时读一下任务行，只要这次有新照片（`newly_added > 0`），不论成功、取消还是失败都按两个开关起后续任务（失败也触发，2026-11-26 拍板）。渲染层只负责显示。

- [ ] **2. 没有调度器，`priority` 字段只用来排列表** · CONFIRMED（调度这件事）/ PLAUSIBLE（实际争抢程度未测）
  `priority` 只在 `db/jobs.py:241` 的 `ORDER BY priority DESC` 里用到，决定活动中心的显示顺序，不决定谁先跑。每种任务各起一个进程、同时跑，只有颜色、相似照片、方向三种做了 `nice(5)`。
  数值含义也不统一：自动补漏 80/85，设置里手动跑 5，导入后人脸 1，默认 50。`startColorsTask` 的注释说自动补漏「排在用户自己的工作之后」，读起来是数字小的优先，列表却是大的排前面。
  后果：监视文件夹来了一批新图，同时人脸 worker、标注、补漏还在跑，大家抢 CPU 和同一把 SQLite 写锁（busy_timeout 5 秒）。
  修法二选一：做一个最小的闸门（导入在跑时后台任务等着；人脸和标注不同时跑），或者不再写 `priority`，明确靠 `nice` 区分前后台，别让字段继续误导。

- [x] **3. 索引和出图是交替的，不重叠** · REFUTED（实测）
  代码确实是交替的：每到 100 张的批次点，`batch_previews`（`job_runner.py:713`）同步跑完这批缩略图，索引才继续。但实测索引 500 个文件只要 0.8 秒，整个导入 21 秒，并行最多省 4%。不做。

- [ ] **4. 目录走了两遍** · CONFIRMED，本地影响可忽略
  `resolve_image_batch` 先 `count_image_files` 数总数，再 `iter_image_files` 处理，两次都是 `sorted(rglob("*"))` 加每个条目一次 `is_file()`。实测第一遍 500 个文件 6 ms；外接盘或 NAS 上没测。
  修法：走一遍存成列表，总数取长度。改动小，放在重新设计的第 6 步顺手做。

- [ ] **5. 手动重新导入已导入的文件夹，每个文件都重读一遍元数据** · CONFIRMED
  `resolve_image` 先 `extract_image_candidate`（ExifTool + 指纹），之后才比对大小和修改时间看变没变；RAW 走 LibRaw，同样如此。监视文件夹和启动补漏事先过滤过，不受影响。实测 500 张没变的文件重新导入 1.1 秒（每张 2.2 ms），和文件夹大小成正比，大文件夹放在 NAS 上会明显。
  修法：先 stat，路径、大小、修改时间都和库里一致时跳过读取。注意 `refresh=True` 还承担「新加了 RAW 源以后重新打分」的作用，跳过读取后要用库里存的元数据打分。

- [x] **6. 索引阶段每个文件提交一次** · REFUTED（本地实测）
  `RESOLVE_BATCH_COMMIT_SIZE = 1` 属实，但本地 507 次提交一共 0.08 秒。图库放在网络盘上（没有 WAL）的情况没测，有人报慢再看。

- [ ] **8. HEIC 走 Pillow 出缩略图，一张 600 ms** · CONFIRMED（实测）
  导入 95% 的时间花在出缩略图上。单张不并发时，24 MP JPEG 要 62 ms，12 MP HEIC 要 601 ms（libheif 没有 JPEG 那种按比例解码）。测试集里 HEIC 只占 20%，却占了约 70% 的出图时间。系统 ImageIO 进程内出同样的缩略图，HEIC 70 ms、JPEG 41 ms；6 路并发出完 500 张要 6.4 秒，现在要 19.7 秒。出图线程从 6 个加到 12 个只快 9%。
  修法：Mac 上用常驻的 ImageIO helper 出缩略图，见重新设计 §4.1。
  进展：已在分支 `perf/import-colors-in-threads` 实现。同一批 500 张，导入 14 秒降到 7.4 秒，CPU 降到三分之一，显示形状完全一致，颜色差异和换个 JPEG 质量同一量级，见重新设计 §1.7。

- [ ] **9. 颜色在写库的主线程上算** · CONFIRMED（实测），现在不是瓶颈，修了 8 以后会是
  `generate_batch` 每出完一张就在主线程调 `analyze_asset_colors`，并发下每张 14.6 ms，500 张 7.3 秒。现在主线程有 11.9 秒在等出图，所以不碍事；缩略图提速到 6.4 秒以后，它就比出图本身还慢。
  修法：照相似照片测量的做法，在出图线程里算调色板，主线程只写库，见重新设计 §4.2。
  进展：已在分支 `perf/import-colors-in-threads` 实现，结果逐行一致；单独合并慢 3%，和第 8 条合在一起才有收益（§1.7 那批里主线程取颜色 10.9 秒，已经比出图还慢），见重新设计 §1.6、§1.7。

- [ ] **10. 人脸识别只有一个 worker，耗时是导入的 5.5 倍** · CONFIRMED（实测）
  500 张 114 秒（每张 228 ms），全程约 1 个核。两个 worker 同时跑，合计吞吐是 1.82 倍。
  修法：多 worker 并发，写库仍在 sidecar 主线程，见重新设计 §6。

- [ ] **11. 导入后的自动标注标的是整个图库，不是这次导入的照片** · CONFIRMED（拍板第 1 条时发现）
  `App.jsx:563` 调的是 `runAnnotation(null, { scope: "all", onlyMissing: true })`：标整个图库里所有还没标注的照片。第一次打开「导入后自动标注」时，库里要是有 1 万张没标注的旧照片，导入 5 张就会一起标掉 1 万张，事先没有提示，花的是用户自己的 API 额度。
  修法：标注任务加一种范围 `import`，按那次导入的时间窗和目录圈定新增的照片，见重新设计 §5.2。已拍板只标这次导入的，是行为变化，和第 1 条一起在第 3 步做。

- [ ] **7. `run_import_job` 重复代码多** · nit
  约 370 行，四个阶段各写了一份几乎一样的进度闭包和 `update_job` 调用；`_build_import_phases` 手写了 5 种模式。可以参照 `_run_single_phase_job` 做成「阶段表 + 一个执行函数」。不影响行为，下次改这里时顺手做。

## 不是问题（REFUTED）

- **Python 计算是瓶颈**：不是。解码在 Pillow、rawpy、pillow-heif，元数据在 ExifTool，视频在 ffmpeg / Swift，人脸在 Core ML，剩下的哈希、k-means、向量距离都是 numpy。把 Python 改写成 Rust 之类的方案在这里收益很小。
- **标注只发 512px 的图**：有意为之。`THUMB_MAX_EDGE = 512`，不管手上是缩略图、HD 还是原图，编码器都会缩到 512，所以用缩略图不损失什么。
- **人脸识别读原图而不是缩略图**：有意为之，画面里的小脸需要分辨率。代价是外接盘上的原图会被完整读两次（出缩略图一次、识别人脸一次），可以接受。
- **每个任务一个独立进程**：合理。崩溃互不影响，渲染层重载不中断任务，也能单独降优先级。

## 建议顺序

实测以后改为按 [import-pipeline-redesign.md §10](../import-pipeline-redesign.md) 的七步做：先 9、8（导入提速最大），再 1、11、2（行为和调度），然后 10，再 5、4，最后把导入排队挪进主进程。待拍板的四条已在 2026-11-26 定下，见重新设计 §11。
