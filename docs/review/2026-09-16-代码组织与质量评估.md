# 代码组织结构 / 代码质量评估（2026-09-16）

配套文件：[2026-09-16-全局代码审查.md](2026-09-16-全局代码审查.md)（正确性缺陷）。这一篇只谈结构与
可维护性，不重复那 9 条 bug。

数据口径：自有代码约 **5.6 万行**（排除 `node_modules` / `.venv`）——
渲染层 34.1k、Electron 主进程 7.4k、Python sidecar 14.7k、Swift native 1.4k。

---

## 先说结论

这是一个**被认真维护过**的代码库，不是那种越滚越乱的个人项目。几个明确的优点：

- **注释质量罕见地高**。密度 7–8%，而且绝大多数是「为什么」而不是「做了什么」——
  `transport.js` 里为什么 secrets 不能走 argv、`main.js` 里为什么透明窗口要用 simple fullscreen、
  `browse.py` 里为什么 person_group 要用 `IN` 而不是相关子查询、`useJobs.js` 里为什么 bridge 要用
  ref。这些是新人（和未来的自己）最贵的信息，一般项目里根本不存在。
- **重构是真的做了，不是喊口号**。`db.py` 拆成 `db/` 包（8 个域模块）、`main.js` 抽出
  `sidecar/transport.js` + `sidecar/commands.js` + 12 个 `ipc/*.js`、编辑器抽出
  `editor/state/`（10 个 hook）+ `editor/render/`（7 个纯函数模块）。而且每次拆分都在文件头注明了
  出处（「review P3-5」「review P3-7」），可追溯。
- **纯逻辑已经被挤出 UI**。`imageMath` / `cropMath` / `splitMath` / `canvasHelpers` / `frameRender` /
  `textState` 都是无 React 依赖的纯函数，并且**有单测**。编辑器这种最容易变成一坨的地方反而是
  分层最干净的地方。
- **并发/一致性这类难点是有意识设计的，不是撞运气**。catalog generation 计数防跨库写、
  jobs 的 cooperative cancel/pause + resume cursor、settings 的 per-catalog 写队列 + 原子
  rename、预览的 `validate_source_unchanged`——这些都有明确的失败模型。
- **CI 有内容**：lint + 三套单测 + build + `npm audit`，外加 19 个 Electron E2E。

下面是问题，按「改了最省事」排序。

## 1. 结构性成本：一个字段要穿过 8 层、4 套命名

加一个「读写 catalog」的功能，调用链是：

```
组件 → api/index.js（门面，~140 个方法）
     → api/client.js invoke
     → preload.js（154 个 ipcRenderer 绑定）
     → ipcMain.handle（134 个 handler，散在 main.js + ipc/*.js）
     → sidecar/commands.js（57 个动词，唯一拼 argv 的地方）
     → sidecar/transport.js（常驻 JSON / one-shot argv）
     → cli.py（490 行 build_parser + 86 个 _cmd_* + 分发表）
     → db/*.py
```

而且同一件事有 **4 个名字**，彼此不自动对齐：

| 层 | 名字 |
|---|---|
| api / preload | `browseImages` |
| IPC channel | `workspace:browse` ← 已经和其它层不同名了 |
| commands 动词 | `browseImages` |
| CLI 子命令 | `browse-images` |

同时还有两个**平行实现**覆盖同一套语义：

- `api/browser/bridge.js`（1206 行）——web 版把这 ~140 个方法在浏览器里重新实现一遍；
- `mcp/server.js`（34 个工具）——给 agent 的第三套入口。

代价可量化：切图工具那个 PR 动了 **22 个文件**，而它甚至**不需要**新增 CLI 命令（复用了主进程的
`processAndSave`）。一个真正落库的功能还要再加 cli parser + handler + db 函数 + commands 动词 +
ipc handler + preload + api/index + browser bridge + MCP tool，约 9 个文件。

**这不是「设计错了」**——Electron 的进程隔离 + Python sidecar + 一个 web 变体 + 一个 agent 入口，
这四个约束确实存在。但有几个地方可以低成本收口：

- **[小] preload + api/index 合并成一张表**。两者已经是 1:1 机械映射（`api/index.js` 文件头自己
  这么写的）。用一个 `channels.js` 声明 `{ method, channel }`，preload 和 api 各自遍历生成，
  少一层手工同步、少一类「加了 preload 忘了加 api」的 bug。
- **[中] `workspace:*` channel 名从 CLI 子命令派生**，消掉 `workspace:browse` vs `browse-images`
  这种漂移。
- **[中] E2E `26-mcp-parity.spec.js` 已经在守 MCP↔IPC 的对齐，但 web bridge 没有对应的守卫**。
  `e2e-web/` 只有 3 个 spec。bridge.js 和桌面 API 漂移了不会有任何东西报警。至少加一条
  「两边导出的方法名集合必须一致」的单测——这是纯静态比对，几十行。

## 2. 拆了一半的 god file

`db.py` 和编辑器拆得很好，但另外几个还是原样：

| 文件 | 行数 | 说明 |
|---|---|---|
| `services/sidecar/.../cli.py` | 2179 | 490 行 `build_parser` + 86 个 `_cmd_*` + 分发表，全在一个文件 |
| `apps/desktop/electron/main.js` | 1846 | 见下 |
| `apps/desktop/src/components/editor/TextPanel.jsx` | 1697 | 单个面板组件 |
| `apps/desktop/electron/mcp/server.js` | 1630 | 34 个工具定义塞在一个数组字面量里 |
| `apps/desktop/src/components/EditorOverlay.jsx` | 1426 | |
| `apps/desktop/src/App.jsx` | 1398 | |
| `apps/desktop/src/hooks/useWorkspace.js` | 1121 | 一个 hook 返回 60+ 个字段 |
| `apps/desktop/src/api/browser/bridge.js` | 1206 | |

`main.js` 尤其值得再推一轮——`ipc/` 这个模式已经建好了，只是有些域搬了、有些没搬。还留在里面的
**独立**职责：

1. **EXIF 载荷构造**（`gcd` / `toExifRational` / `toExifGpsCoordinate` / `buildExifPayload` /
   `formatExifDateTime`，约 100 行）——纯数学，零 Electron 依赖，**零测试**，而且
   `readSourceMetadataForExport` 还在用 `runPythonJson` 内联一段 Python 源码字符串（打包态
   `python3` 未必存在，代码里自己也承认）。搬去 `electron/exif.js` 并补单测，收益立竿见影。
2. **token 加解密**（safeStorage + legacy 明文迁移）→ `electron/tokens.js`
3. **media:// 白名单 + 协议处理 + 视频 HTTP server** → `electron/media/`
4. **catalog 生命周期**（resolve / normalize / create / switch / prepare / sample）→ `electron/catalog.js`
5. **任务启动器**（import / enrichment / preview / ai_repaint / text_image + `formatJobStatus`）→ `electron/tasks.js`
6. **窗口 + 菜单 + 全屏**、**原生拖出**、**外部 open-file 队列**、**handwriting 缓存 LRU**

顺带一提，注入规模已经偏大了：`createMcpServer` 收 **20 个依赖**，`aiIpc.register` 15 个、
`jobsIpc` / `assetsIpc` 13 个。这既是拆分做得好的证据（有清晰的 seam，可测），也是信号：
`formatJobStatus` / `latestJobStatus` / `createJob` 被传给 5 个模块，它们本来就该是一个
`tasks` 模块的导出，而不是从 `main.js` 往下发的参数。

## 3. 抽象漏了：单一出口被绕过 + 复制粘贴

- **`sidecar/commands.js` 的文件头写着「唯一拼 argv 的地方 …… 两个入口曾经各拼各的、已经漂移过
  （docs/review-2026-06.md P3-3）」，但现在又有 10 处直接调 `callSidecarAsync` / `callSidecarJsonAsync`
  绕过它**：`summary`(×2)、`catalog-roots`、`list-tags`、`get-annotation`、`clear-ai-location`、
  `list-repaint-history`、`collage-sources`、`get-provider-token`、`split-shared-assets`、
  `repair-resource-sets`。同一个坑正在重新长出来。补齐这 10 个动词、然后**不再把
  `callSidecarJsonAsync` 传给 ipc 模块**（只传 `commands`），这条约束才是可执行的。
- **`panelBoundaries` 在两个进程里各写了一份**（`ipc/saveFile.js` 和 `editor/splitMath.js`）。
  这是无缝切图的核心不变量——两边一旦漂移，切出来的图就有缝或重叠，而且只有 E2E 能发现。
  应该只留 `splitMath.js` 一份，主进程 `require` 过去（纯函数，没有 React 依赖，可以跨进程共享）。
- **`hexToRgba` 有 4 份**（`canvasHelpers.js` 是规范版，`TextPanel.jsx` / `TextCanvas.jsx` /
  `ColorPickerPopover.jsx` 各自又写了一遍），而且**已经不一致**：TextCanvas 那份处理
  `"transparent"`，ColorPicker 那份输出带空格。改主题色相关逻辑时很容易只改一处。

## 4. 质量债：77 条 eslint 抑制，其中 42 条是死代码

`eslint-suppressions.json` 覆盖 21 个文件：

- **`no-unused-vars` × 42** —— 这些不是误报，是**真死代码**：`EditorOverlay.jsx` 里的
  `executeSave` / `beginRotate` / `pointerPoint` / `resizeCropRect` / `canvasToBlob` /
  `getTextLayers`，`AiRepaintPanel.jsx` 里的 `PROVIDER_TYPES` / `generateInstanceId` /
  `generateInstanceName`，`App.jsx` 里的 `person_group` / `selectedIdSet` / `moveSelection`，
  以及一堆没用上的 lucide 图标。**直接删**，改完 eslint 自己会挡住回潮。这是这份清单里
  投入产出比最高的一条。
- **`react-hooks/exhaustive-deps` × 35** —— 这个不能一把梭。它是 stale-closure 类 bug 的
  温床（本次 review 里 `useJobs` 的 bridge-ref 模式、`useWorkspace` 的 `jobsBridgeRef.browseContext`
  都是在绕它）。建议按文件逐个消化，每消掉一个就从抑制表里删一行——抑制表本身就是很好的进度条。

另外：**Python 侧没有任何 lint / 类型检查**。14.7k 行、类型标注已经写得相当完整（`from __future__
import annotations` + 全量 signature），却没有 ruff、没有 mypy，CI 里也只跑 unittest。
加一行 `ruff check` + 一行 `mypy --ignore-missing-imports` 是半小时的事，能直接接住本次 review 里
`catalogHasDb` 那一类的同构错误（Python 版就是「忘了调用」「拼错 kwarg」）。

## 5. 测试金字塔是倒的

| 层 | 数量 | 覆盖对象 |
|---|---|---|
| E2E（Playwright） | 38 spec | 几乎所有功能 |
| 渲染层单测（vitest） | 13 文件 / 82 case | 只有编辑器纯数学 + format + 地图 antimeridian |
| 主进程单测（node:test） | 4 文件 / 12 case | settingsStore、transport、sampleCatalog、（本次新增）saveFile |
| Python 单测 | 19 文件 / 93 case | 覆盖较好 |

问题不在总量，在**分布**：

- `useWorkspace.js`（1121 行，管着 browse 分页 / 选中 / 请求竞态 / catalog 事件 / 乐观更新）
  **一条单测都没有**，只能靠 E2E。本次 review 里 `filteredItems` 那条 bug 正好长在这里——
  它是纯函数，本来一条断言就能挡住。
- 主进程的图像/EXIF 数学（`buildExifPayload`、`toExifGpsCoordinate`、`pileSafeDragIcon`）同样
  零测试，而 `buildRegionPipeline` 的方位 bug 就是这类「纯数学、无 UI、错了肉眼很难发现」的
  典型——加了穷举单测之后 128 种组合一次就暴露了 32 种错误。
- **CI 只跑 19/38 个 E2E**（workflow 里注明了原因：GitHub macOS runner 没 GPU、AVFoundation 不稳、
  fs-watch 时序飘）。理由成立，但意味着**另一半 E2E 只在有人记得跑 `npm run e2e:only` 时才跑**。
  建议至少加一个 nightly / release-tag 触发的完整 E2E job，别让它只靠人的记性。

**建议的下一步**：把纯逻辑从 `useWorkspace` 里挤出去（`browseScopeKey`、`filteredItems` 的谓词、
`loadBrowser` 的「哪个选中还有效」决策、`revealRelatedAsset` 的 `resetScope` 判定），放进
`hooks/workspaceLogic.js` 加单测。这和编辑器当初把数学挤进 `imageMath` / `cropMath` 是同一招，
那一招在这个库里已经证明有效。

## 6. 零散的

- **没有 TypeScript，也几乎没有 JSDoc**（全仓 `@param`/`@returns` 只有 16 处）。5.6 万行 JS 全靠
  命名和注释维持契约。不建议现在整体迁移 TS（成本太高），但**跨进程边界**（preload 契约、
  IPC payload、MCP 工具的 inputSchema ↔ handler 实参）是最值得先补 JSDoc 或 `.d.ts` 的地方——
  这正是编译器帮不上忙、最容易悄悄漂移的三条缝。
- **`docs/` 有 37 个文件，大部分是 `*-plan.md`**。计划文档写得很好，但完工之后没有归档机制，
  新人分不清哪些是「现状的权威描述」（`agent-native-mcp.md`、`image-asset-model.md`）哪些是
  「已完成的历史计划」（`foundation-refactor-plan.md`、`mcp-parity-plan.md`）。建议加
  `docs/archive/`，或者在每个 plan 顶部加一行状态标记。
- **`site/`、`marketing/`、`research/`、`RESOURCES/`、`tmp/`、`test-results/` 和代码同级**。
  仓库根目录有 27 个条目，其中只有 4 个是代码。不影响构建，但第一眼很难看出这是什么项目。
