# AfterFrame 0.5.8 文件移动、删除和恢复：真实使用与 E2E 缺口

> 2026-10-05 复核：各条目已标注处理结果。修复在分支 `review/real-use-2026-10-04` 上，已经 PR #169 合并到 main（`fbea8f7`）；测试结果、外接盘真实 UI 复核和仍未覆盖的范围见文末“复核结论”。

本轮通过原生 UI 测试已经入库的图片在访达中移动、改名、移到废纸篓、放回原处，以及应用内重新连接、从图库移除和从磁盘删除。主要结论：放回原路径可以继续使用原记录及其评分；新路径导入会产生另一条记录，旧评分和文件夹关联留在缺失记录上；使用“重新连接”可以保留原记录，但新路径若已入库会被拒绝。确认了一个 P2 界面问题：当前选中照片的详情面板不会随刷新或重新连接同步文件状态。

测试日期：2026 年 10 月 4 日，America/Los_Angeles。安装版为 `/Applications/AfterFrame.app` 的 0.5.8。源码与 E2E 对照 HEAD：`81b4748bec510135280bd2aeda32a8357ee036a7`；发布标签 v0.5.8：`225c847904e7cc65a021e345da940541df3e6137`。本轮涉及的 `useWorkspace.js`、`Inspector.jsx`、`watcher.js` 和 `db/maintenance.py` 在这两个版本间没有差异。本次未运行 HEAD 的全套自动化测试，也没有修改产品代码。

此前的大规模导入、编辑、拼图、人物、地图等测试见 [完整真实使用报告](./2026-10-04-AfterFrame真实使用与E2E缺口.md)。本文中的路径移动指磁盘上的文件移动；应用的“加入文件夹”指图库逻辑分组，两者分别观察。

## 隔离样本与操作方式

图库仍为 `/Volumes/G-DRIVE PRO/CUA 用户旅程.afcatalog`，没有在内置硬盘新建图库。测试源目录为 `/Volumes/G-DRIVE PRO/CUA_FileLifecycle/A` 和 `B`。所有移动和删除均针对测试导出 `derived/CUA_collage_swap.jpg` 的副本，用户原始照片和原始导出保持完整。

初始三张副本分别为 `Lifecycle_external.jpg`、`Lifecycle_catalog.jpg`、`Lifecycle_trash.jpg`，2048×1152、347890 字节，内容相同。分别设置四星、三星、二星，并加入 `CUA 文件生命周期`。监控分支又在 B 创建一张副本，设五星加入文件夹；移动到 A 后产生的另一条记录设一星。评分用于追踪记录是否保留，图库的“重复项”提示也是预期结果。本轮没有对 RAW+JPEG 资源组、编辑版本、人物关联或 AI 标注分别设置恢复断言，不能把 JPEG 单文件结果推广为这些关系已经验证。

导入、搜索、评分、菜单、重新连接的系统文件选择器、监控设置、退出和重启均通过 AfterFrame UI；复制、移动、改名、废纸篓恢复通过访达 UI。只读 SQLite 查询用于核对资产身份、评分、文件夹关联、删除抑制记录与最终状态，没有通过 SQL 修改图库。用户明确确认后才执行了两个应用内删除。

## 确认的缺陷

- [x] **P2 当前选中照片的 Inspector 在文件缺失、恢复或重新连接后保留旧状态 — CONFIRMED，已修复（`b78aad4`）**

  复现第一方向：选中 A 的 `Lifecycle_external.jpg`，在访达将它移动到 B，回到图库点刷新。卡片已经显示“缺失”，Inspector 仍显示原路径的普通源文件信息，没有缺失提示和“重新连接”。再次点同一张卡片也没有恢复。先选另一张再选回来，Inspector 才显示缺失提示和重新连接按钮。

  复现反方向：通过该按钮的原生文件选择器重新连接到 B。卡片变为正常，数据库路径已变为 B，四星仍在；Inspector 仍显示“缺失”和旧 A 路径。换选后才显示正确 B 路径。恢复原路径与监控恢复分支也观察到相同详情状态滞后。

  源码依据：`apps/desktop/src/hooks/useWorkspace.js:333` 更新列表，但 `:340` 只在选中的资产 ID 改变时调用 `loadDetail`。文件状态变化或重新连接没有改变 ID，因此已加载详情保留。`components/Inspector.jsx:173` 成功重新连接后调用 `onRelinked`，`App.jsx:1415` 将其接到 `refreshAll({ force: true })`，仍走这条选择保留路径。相关代码与 v0.5.8 相同。

  E2E 缺口：`apps/desktop/e2e/12-missing-original.spec.js:57` 在首次选择前已经删除副本并执行校验、刷新；`:76` 随后才点卡片验证提示。因此没有覆盖“已选中→文件变化→刷新”。`:91` 通过 API 重新连接，再断言卡片缺失标记消失和评分保留，没有断言仍打开的 Inspector 同步更新，也没有走原生重新连接选择器。

  建议断言：保持同一资产选中，依次外部移动、刷新、原路径恢复、刷新、原生重新连接到新路径。每一步同时核对卡片状态、详情中的路径／缺失提示／重新连接按钮和编辑可用性，不通过换选来掩盖同步问题。

  **复核与修复（2026-10-04）**：当前 HEAD `c864ac0` 与报告基线只差一个 CSS 提交，缺陷仍在。先按上面的建议断言写 E2E，复现为“卡片显示缺失、仍选中的 Inspector 没有缺失提示”。修复 `b78aad4`：`loadBrowser` 保留同一选中时，用户触发的刷新（工具栏刷新、重新连接、校验文件）一律重读当前详情；后台刷新（监控导入、导入期间轮询、catalog-changed）比较新行与详情的路径、实时文件状态、评分和元数据，不一致才重读（`workspaceLogic.detailIsStale`，有单测）。

  `e2e/60-file-lifecycle.spec.js`（已加入 CI 子集）全程不换选：外部移动→刷新→原路径放回→刷新→移到“废纸篓”目录再放回→移动后点 Inspector 的“重新连接”选择 B→改名并导入后再重新连接到已入库路径被拒。每一步同时核对磁盘、卡片缺失标记、Inspector 路径／缺失提示／重新连接按钮、评分、文件夹成员、预览解码和编辑可用性。重新连接的原生选择器由主进程应答（Playwright 无法操作系统面板），其余链路为真实 UI。监控目录放回后由监控导入触发的同步在 60 的本地用例中覆盖。把修复改回旧逻辑后，这三处断言均失败。外接盘真实 UI 复核见文末。

## 已确认的行为与需要补齐的 E2E

- [x] **新路径导入与重新连接是两种不同身份操作，移动或改名会留下旧评分记录 — CONFIRMED（行为与覆盖缺口），覆盖已补齐（`b78aad4`），行为未改**

  未监控时只有手动导入新位置才出现新条目；监控时新位置自动入库。两条路径都没有自动迁移旧评分和文件夹关联。显式重新连接能保留原身份，但新路径已被另一条记录占用时会返回 `path_in_use`。这不能直接判定为数据丢失：旧元数据仍在缺失记录上；当前产品没有在这条流程自动追踪移动或合并记录。

  源码依据：`services/sidecar/src/media_workspace/db/maintenance.py:63` 的 `relink_asset` 原位改路径，`:117` 检查目标是否被其他资产占用；`components/Inspector.jsx:176` 显示冲突提示。`electron/watcher.js:72` 的 `flush` 只把当前仍存在的媒体路径发往导入流程，`:79` 丢弃已经不存在的路径事件，不能据此配对新旧路径。

  E2E 缺口：`17-watched-dirs.spec.js:65` 验证新增文件，`:75` 验证原路径覆盖后资产 ID 与预览变化；没有外部改名、跨目录移动、先复制再改名、旧路径恢复和新路径冲突的连续流程。该 suite 在 `:19` 整体跳过 CI，理由是 macOS runner 文件事件投递慢且不均匀。现有正常导入与覆盖断言不能代表移动／删除分支持续受 CI 保护。

  建议将“同一路径恢复”和“不同路径新增”分别写清预期；检查资产 ID、卡片数量、评分、文件夹成员、缺失记录、预览文件和原生重新连接冲突提示。若产品决定支持自动追踪移动，应另外明确重复内容、多份副本与目标已入库时的合并规则。

  **复核（2026-10-04）**：按要求没有改变产品行为，不自动追踪移动，也不合并记录。`e2e/60` 把两种身份操作分开断言：
  - 改名后显式导入得到新记录，未评分、不在原文件夹；旧记录保留评分和文件夹。
  - 把旧记录重新连接到已入库路径时出现冲突提示，两条记录都不变。
  - 监控目录中的改名和跨目录移动，在 60 的 “a watched folder while the app runs” 中断言：新记录无评分，旧记录缺失且保留五星和文件夹。该组与 17 一样在 CI 跳过（文件事件投递不稳定），只在本地运行，本次本地通过。
  - 应用关闭期间的改名加跨目录移动，由启动补扫处理。这一段不依赖文件事件，放在 CI 可跑的用例中。

  仍未覆盖：先复制再改名留下的中间名记录。它取决于两次操作与监控导入间隔的先后，没有写成确定性断言。

- [x] **外部删除恢复、图库移除后重新导入、磁盘删除后恢复需要分别验证 — CONFIRMED（行为与覆盖缺口），覆盖已补齐（`b78aad4`）**

  外部删除只是原路径临时不存在，旧图库记录保留，原路径恢复后继续使用旧评分。应用内从图库移除则删除旧记录及关联；监控补扫抑制未变化的同路径文件，显式手动导入才将其带回。应用内磁盘删除先移动到系统废纸篓，再移除图库记录；文件可恢复不等于评分和文件夹关联可恢复。

  两张应用内删除的测试图片重新入库后，资产 ID 的字符串恰好仍与删除前相同，但 `app_rating` 均为 null，文件夹成员数均为 0。因此仅断言恢复后的 ID 相同，无法证明旧记录的元数据被恢复。图库删除后的重启补扫任务实测 `skipped_deleted=1`、新增 0；手动全库导入随后新增 1。废纸篓恢复任务实测新增 1、已入库跳过 1，预览失败 0；这次任务同时处理了排队中的手动文件导入，所以不能把它称作独立、空闲情况下的实时恢复时延测试。

  源码依据：`db/maintenance.py:273` 为仍在磁盘的路径记录删除抑制信息，`:298` 删除资产与相关记录；`reverse_lookup.py:343` 以路径、大小和修改时间判断抑制是否仍有效，`:391` 区分自动与手动导入。`electron/ipc/assets.js:93` 先 `shell.trashItem` 再删除记录；此时源路径已不存在，所以不记录该路径的删除抑制信息。

  E2E 缺口：`39-context-menu-selection.spec.js:164` 已覆盖磁盘删除确认框、取消、成功移到废纸篓，并断言卡片和原路径文件消失；测试在这里结束，没有 Put Back、监控重新入库或元数据恢复断言。`36-mcp-jobs-tools.spec.js:163` 已覆盖 API 从图库移除、预览删除、原文件保留，未继续验证启动补扫的抑制、显式手动导入解除抑制和两种删除恢复的差异。应在现有测试上延长完整生命周期，不能把“删除有 E2E”误写成“删除后恢复也有 E2E”。

  **复核（2026-10-04）**：`e2e/60` 中 CI 可跑的部分分别覆盖了三条路径。恢复与否以评分和文件夹成员判断，不以资产 ID 相同为依据。
  - 外部删除：用测试目录模拟访达废纸篓，路径消失后同一字节放回原路径。同一记录的评分、文件夹和预览恢复。
  - 从图库删除：文件保留，记录、评分和文件夹成员移除。重启后启动补扫不把它带回；同一次补扫导入了关闭期间改名的文件，证明补扫确实运行过。之后通过工具栏导入显式选择原文件，图片回到图库，评分和文件夹不恢复。
  - 从磁盘删除：取消不改变任何东西。确认后文件进入系统废纸篓，记录移除。同一字节放回原路径后，启动补扫重新入库，评分和文件夹不恢复。自动化用例只覆盖启动补扫这条路径；在监控目录中放回、由实时监控重新入库，是在文末的外接盘复核 F7 中验证的。

## 收尾与边界

测试监控只覆盖 `CUA_FileLifecycle`，完成后移除该监控目录；不监控整个外接盘。最终保留隔离副本和历史缺失记录，方便检查移动前后的评分差异。所有用户原始照片未移动、删除或覆写，废纸篓中其他内容没有操作。本轮不包含外接盘拔出／重新挂载、目录整体移动、大批量删除、RAW+JPEG 组内部分文件恢复、文件内容不同的强制重新连接或跨 Catalog 转移。
