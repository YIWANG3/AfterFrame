## P0

- [x] **CONFIRMED · `buildRegionPipeline` 的方位合成用了「角度相加 + 镜像异或」,128 种组合里 32 种导出图比预览多转 180°**
  `apps/desktop/electron/ipc/saveFile.js`（`buildRegionPipeline` 的 stage 1）

  旋转和镜像不对易（`R_θ ∘ F = F ∘ R_−θ`），所以「EXIF 角 + 用户角相加、EXIF flop 与用户 flipX
  异或」这种合成方式是错的——它丢掉了那个符号翻转。原注释还假设 sharp 的管线顺序是
  `rotate → flop`；实测 **sharp 在同一条管线内总是先 flip/flop 再 rotate**，与调用顺序无关
  （`.rotate(90).flop()` 和 `.flop().rotate(90)` 输出完全相同），于是 EXIF_MAP 里对镜像方位的
  角度取负也是多余的。

  把 8 种 EXIF 方位 × 4 档 quarterTurns × flipX × flipY = 128 种组合跟 canvas 预览
  （`buildTransformedCanvas`,浏览器已定向的 `<img>` 上做 `translate → rotate → scale`)逐像素对比，
  旧代码 **32 种不一致**，都是差 180°：

  - orientation **5 / 7**（带镜像）：即使不做任何编辑，导出就已经转错。
  - orientation **5 / 6 / 7 / 8**（竖拍手机照的常规方位）：只要用户做了**奇数次镜像**
    （单独水平翻转、或单独垂直翻转），无论转不转，导出都错。

  也就是说「手机竖拍照片 + 水平翻转 + 保存」这种日常操作就会踩中。触发路径是编辑器快速保存 /
  导出的 sharp 快速路径（`saveImage.js` 在无图层、无边距、无 scrim 时走它）、无缝切图的
  `processAndSavePanels`、以及 MCP `crop_assets` 的 rect/rotate 模式；裁剪框基准跟着一起错位。

  **修法**：不要手工合成。把每个变换写成 D4 群的正规形 `R_angle ∘ Fx^flop`（镜像在前、旋转在后
  ——正好是 sharp 和 canvas 的原生顺序），用真正的群乘法
  `(R_a ∘ F^m) ∘ (R_b ∘ F^n) = R_(a ± b) ∘ F^(m xor n)` 依次合成 EXIF → flipX → flipY →
  quarterTurns。输出尺寸也改成「合成角是 90/270 才交换」，不再单独跟踪 `orientSwaps`。

  **回归测试**：新增 `apps/desktop/electron/ipc/saveFile.test.js`，穷举那 128 种组合对齐 canvas
  预览的参考实现（分步、单操作的 sharp 管线），另加一条「无编辑时必须等于 sharp 自动定向」。

- [x] **CONFIRMED · 任务轮询把「查询失败」当成「任务已结束」,长任务会从 JobDock 凭空消失**
  `apps/desktop/src/hooks/useJobs.js:79` + `apps/desktop/electron/ipc/jobs.js:54`

  两层都把异常吞成空数组：主进程 `workspace:active-jobs` 的 `catch { return []; }`，渲染层
  `pollActiveJobsOnce` 的 `catch { jobs = []; }`。随后 `liveIds` 为空 → `knownActiveRef` 里
  所有任务都被判定为「已完成」→ 逐个触发 `handleJobFinished`（refreshAll、mirrorTask 写入陈旧
  终态、preview-hd 链式启动、完成 toast），并且 `jobs.length === 0` 让轮询彻底停下
  （`jobsPollingRef.current = false`）。

  触发场景：常驻 sidecar 是严格串行的（见 `transport.js` 里 `AFTERFRAME_SIDECAR_TRACE` 的注释），
  大批量导入时一次 `list-active-jobs` 超过 30s 超时即可复现——导入仍在跑，但 UI 认为它结束了、
  刷新了图库、并停止轮询，直到下一次 `pokeJobs`。

  修法：区分「请求失败」和「空列表」，失败时保持 `knownActiveRef` 不变并继续下一次轮询。

## P1

- [x] **CONFIRMED · `clearPreviewCache` 从未导出,切库时 MCP 预览缓存不会清**
  `apps/desktop/electron/mcp/server.js:1627` / 调用点 `apps/desktop/electron/main.js:1361`

  `switchCatalogTo` 里写着「Per-catalog caches must not leak across libraries: … and the MCP
  preview-path cache」并调用 `mcpServerApi?.clearPreviewCache?.()`，但 `createMcpServer` 只
  `return { start, server, port }`，全文件没有 `clearPreviewCache` 的定义。可选链让它静默 no-op。

  `previewPathCache` 还是**模块级** `Map`，而 `asset_id` 是内容指纹 + 路径的稳定哈希
  （`metadata.py:102 stable_asset_id`）——同一张照片在两个 catalog 里 id 相同。于是：agent 在
  A 库搜过图 → 用户切到 B 库 → agent 请求 `/assets/{id}`，拿到的是 **A 库**的预览文件。

  修法：导出一个清空 `previewPathCache` 的函数（或把 Map 移进 `createMcpServer` 闭包并在切库时重建）。

- [x] **CONFIRMED · 10 分钟心跳收割会误杀正常运行的 AI 重绘任务**
  `services/sidecar/src/media_workspace/db/jobs.py:213`（`list_active_jobs`）

  `list_active_jobs` 每次被调用都会把 `updated_at` 超过 10 分钟的 queued/running 行标记为
  `failed`。而 `run_ai_repaint_job`（`job_runner.py:1105`）只在开头写一次 `status="running"`，
  之后整段远程调用期间没有任何 `update_job` 心跳。

  即梦的 `_jimeng_submit_poll_extract`（`ai_repaint.py:545`）最多轮询 180 次、每次 `sleep(2)`，
  命中并发限流（code 50430）时再额外 `sleep(5)`——最坏 180 × 7s ≈ **21 分钟**。渲染层每 1.2s 调
  一次 `list-active-jobs`，所以一定会在第 10 分钟把这条正在跑的任务打成
  「stalled — no heartbeat for 10 minutes」。用户看到任务失败，`useJobs` 触发完成副作用；几分钟
  后子进程成功返回又把行改回 succeeded，但 UI 已经走远了。

  修法：给长阻塞任务加心跳（轮询循环里定期 `update_job`），或按 job_type 区分收割阈值。

- [x] **CONFIRMED · `ipc/annotation.js` 里 4 处 `catalogHasDb` 守卫恒真,形同虚设**
  `apps/desktop/electron/ipc/annotation.js:98, 215, 222, 229`

  `const { catalogHasDb } = getCatalogState();` 拿到的是**函数**，`if (!catalogHasDb)` 永远为
  false。同文件 206 行写的是 `if (!catalogHasDb())`，说明是复制粘贴时漏了括号。

  未开 catalog（打包版首次启动、欢迎页）时：`workspace:get-annotation` / `workspace:list-tags` /
  `workspace:clear-ai-location` 不会返回 `null` / `[]`，而是一路走到 `sidecarCommand()` 抛出
  `No catalog is open`，IPC invoke 在渲染层 reject；`workspace:annotate-asset` 同理，用户看到的
  是内部报错而不是「Open a catalog before annotating assets.」。

- [x] **CONFIRMED · 图库对服务端搜索结果做了二次本地过滤,caption / OCR / tag 命中全被丢掉**
  `apps/desktop/src/hooks/useWorkspace.js:155`（`filteredItems`）

  服务端 `_search_clause`（`db/browse.py`）匹配 stem、image_path、camera、lens、**anno.caption、
  anno.detected_text、asset_tags**；`filteredItems` 只在 stem / primary_stem / image_path /
  raw_path / version_kind / camera_model 上再过滤一遍，且 `App.jsx:315` 渲染的就是它。

  结果：搜一个只出现在 AI 描述、OCR 文本或标签里的词，sidecar 返回了正确的若干行，前端把它们**全部**
  过滤掉，图库显示为空。这不是「防抖期间的临时态」——`filteredItems` 是纯 memo，服务端结果回来后
  依然在过滤。

  代码里已经有人撞到过：`revealRelatedAsset` 特地写了
  `// The local text projection may hide a server-side annotation match.`（`useWorkspace.js:402`）
  来绕开它，但主图库没修。

  修法：搜索走服务端时直接用 `items`；或把 caption / detected_text / tags 补进本地谓词。

- [x] **CONFIRMED · MCP `import_directory` 在已有导入运行时静默不导入,却报告成功**
  `apps/desktop/electron/mcp/server.js:578` → `main.js:786`

  `startImportTask` 发现 `latestJobStatus("import").running` 就直接返回**那个已存在的任务**，
  完全忽略本次请求的目录。MCP 工具拿着别人的 `job_id` 轮询，等它结束后返回
  `{ done: true, status: "succeeded", result: … }`。

  触发场景：watched 目录的自动导入正在跑时，agent 调 `import_directory` → 目录被 `registerRoots`
  注册了、但从未被导入，工具却回报成功。UI 侧不存在这个问题，因为
  `addImagesFromPaths`（`useWorkspace.js:841`）在 `importTask?.running` 时会塞进 `pendingImport`
  队列，由 `useJobs` 的 import 完成回调续跑；MCP 路径没有这层队列。

## 已排查但驳回（REFUTED，留档避免重复怀疑）

- **「用户翻转 + 90° 旋转」在 orientation 1 上也会错** —— REFUTED（仅限 orientation 1）。
  最初按「sharp 先 rotate 后 flop」推导出所有翻转都差 180°。实测 sharp 在单条管线内固定先
  flop 后 rotate，恰好与 canvas 的 `translate → rotate → scale → drawImage`（scale 先作用）同序，
  所以 EXIF 方位为 1（无旋转无镜像）时旧代码逐像素正确。错的是方位 5–8，见 P0 第一条的 32/128。

- **`locate_image_asset` 与 `list_image_assets` 的 JOIN 集合不同,分页位置会错位** —— REFUTED。
  `list_image_assets` 多出的 LEFT JOIN 都是 1:1：`preview_entries.cache_key` 由
  `sha1(asset_id:kind)` 决定（`db/assets.py:666`），`resource_set_items` 主键是 `(set_id, asset_id)`
  且 `attach_asset_to_resource_set` 命中已有集合就提前返回，不会产生行放大。

- **常驻 `serve` 模式下子进程写 stdout 会污染 JSON-lines 协议** —— REFUTED。
  `preview_service.py` / `video.py` 里所有 `subprocess.run` 都带 `capture_output=True`，
  fd 1 不会被继承污染。

- **`flushExternalImports` 在窗口未就绪时丢弃待导入文件** —— REFUTED。
  它保留 `pendingExternalImports` 并依赖 `did-finish-load` 回调重放（`main.js` `createWindow`），
  该事件在每次 load / reload 都会触发。
