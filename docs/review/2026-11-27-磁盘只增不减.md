# 磁盘只增不减（2026-11-27）

起因：清理时发现 `$TMPDIR` 一天攒了 4.5 GB 的 `FaceEmbedding_*.mlmodelc`。于是把打包版会往磁盘写的地方全查了一遍
（代码审计 + 本机 `~/Desktop/main.afcatalog`、userData、`$TMPDIR` 实测），看还有哪些只增不减。
数据库是拷到 scratchpad 上查的，没碰真图库。行号以当时的 main（`fa313dd0`）为准。

## CONFIRMED

- [x] **people-worker 每次启动把模型编译进 `$TMPDIR`，从不删**（`native/people-worker.swift` init 里的
  `MLModel.compileModel`）。一次扫描 3 个 worker 就是 3 份，每份 125 MB；打包版装的也是 `.mlpackage`。
  → #359（编译一次，放 userData 固定位置；待合并）；#361 在 macOS 启动时清掉旧版本留在 Core ML 临时目录里、超过 10 分钟的副本（待合并）。
- [x] **`userData/video-proxies/` 没有任何清理**（`electron/ipc/video.js` `app:video-proxy`）。key 是
  `路径:大小:mtime`，源文件一改就多一份；每个灯箱里放不了的视频转一份 ≤1080p H.264，FFmpeg 那条路约 60 MB/分钟。
  本机没有这个目录（片子都能直接播），但对有 HEVC/ProRes 之类视频的用户是最大的一块。
  → #360：LRU 抽成 `electron/media/cacheBudget.js`，视频代理留最近 2 GB（待合并）。
- [x] **`catalog.sqlite3.schema<N>.bak` 每次升级留一份完整数据库，从不删**（`db/core.py`
  `_backup_before_migration`，「One per old version, never overwritten」）。本机 schema 8 到 15 共 7 份约 365 MB，
  图库越大每份越大。旧的几份已经回不去了（缺几个月的数据）。
  → #362：只留编号最大的 2 份，迁移成功后和打开已是最新的图库时都会清（待合并）。
- [x] **`userData/video-keyframes/` 没有清理**，设置页的缓存目录列表里也没有它（`video.js` `app:video-keyframes`）。
  本机 245 个目录 65 MB（main 图库 137 个视频，其余来自别的图库和改过的源文件）。
  → #360：留最近 256 MB，设置页加了「视频悬停预览帧」一行（待合并）。
- [x] **`userData/depth-cache/` 没有清理**（`electron/ipc/depth.js`）。本机 106 个 5 MB，量小。
  → #360：留最近 256 MB（待合并）。
- [x] **「从图库移除」不删 app 自己在 `derived/` 里生成的文件**。只有「从磁盘删除」会挪进废纸篓
  （`electron/ipc/assets.js`）；移除只写一条 `deleted_files` 墓碑。本机有 10 个 `collage_*_p1_text_*.jpg`（10-06，16 MB）
  已有墓碑、文件还在。AI 重绘结果写在原图旁边（`tasks.js`），同样只在「从磁盘删除」时清。
  原图不归 app 管，留着没错；`derived/` 是 app 自己的东西。改成移除也挪废纸篓属于改既有行为，用户拍板做。
  → #364：`electron/derivedFiles.js`，界面和 MCP `delete_assets` 都走它；AI 重绘结果（在原图旁边）没动（待合并）。
- [x] **贴纸识别失败时临时目录漏删**（`features/sticker/electron/stickers.js`）。`afterframe-sticker-*` 先 mkdir，
  之后「Selection is too small」、工具退出码非 0、没有 manifest、sharp 报错都会直接抛，目录没交给渲染层，没人删；
  识别结果显示时关窗口也一样（React 卸载清理不会跑）。每次可达几十 MB，在 `$TMPDIR`，macOS 约 3 天后会清。
  → #363：失败时先删再抛；启动时清掉一天以前的 `afterframe-sticker-*`（待合并）。
- [x] **每个 sidecar 进程留一个 `afterframe-print-probe-<pid>.jpg`**（`visual.py` `_probe_image`）。每个约 1.3 KB，
  但每个后台任务进程一个；这天 `$TMPDIR` 里有 833 个（大多是 e2e 跑出来的）。→ #363：所有进程共用一个 `afterframe-print-probe.jpg`（待合并）。
- [ ] **`jobs` 表从不清**（没有任何 `DELETE FROM jobs`，界面只列 20 条）。本机 5 个月 986 行 2.3 MB，量很小，低优先，没做。
- [x] **三个单测不删自己的临时目录**：`features/repaint/electron/repaint.test.js`（`af-repaint-`，每次约 8 个）、
  `features/sticker/electron/stickers.test.js`（`af-stickers-`）、`electron/ipc/video.test.js`（`afterframe-video-ipc-`，
  只删了 `afterframe-video-stall-`）。实测跑一次 check 几分钟内多出 16 + 14 + 8 个。只影响开发机。
  → #363（待合并）。

## PLAUSIBLE

- [ ] 多数 e2e spec 在模块顶层 `mkdtempSync`，Playwright 收集用例时也会加载 spec，可能每次多留一个目录（没验证）。
- [ ] `transcode-cache` 崩溃后留下的 `.<key>.<pid>.partial.jpg` 永远不会被 LRU 清掉（过滤跳过了点文件）。
- [ ] sidecar 没装 SIGTERM 处理，`withCatalogPaused` 杀进程时 `finally` / `TemporaryDirectory` 不会跑，
  `media-workspace-sips-*`、`media-workspace-ql-*`、`afvframes-*` 会留下。量小。

## 没看到 / 不成立

- 换人脸模型后旧模型的 `asset_faces` 行留着：本机只有当前的 arcface `b51b655`（1129 行）和宠物 dinov2 `ed25f3a`（18 行），没看到旧模型的行。
- WAL 停在高水位：app 运行时 main 图库没有 `-wal` 文件，freelist 只有 56 页。
- userData 里 750 MB 的 Chromium `Cache`：抽样几乎全是开发版 Vite（`127.0.0.1:5173`）的缓存，Chromium 自己有上限，
  打包版走 `file://`。原因是开发版和安装版共用一个 userData（`afterframe` 和 `AfterFrame` 在不区分大小写的磁盘上是同一个目录）。
- 有上限、没问题的：`transcode-cache`（LRU 1 GiB）、`handwriting-cache`（200 MB）、`raw-edit-cache`（留 6 个）、
  `depth-models`（留 1 个）、设置备份（每个文件留 3 份）、更新器下载目录（下次更新前清空）。
- 图库内：8078 个预览文件和 `preview_entries` 一一对应；各 per-asset 表都是 `ON DELETE CASCADE`，没有孤儿行。
- app 不写日志文件（主进程只打到控制台，后台任务进程 `stdio: "ignore"`），所以没有日志膨胀。
